# coopfix4g 回归测试候选（官方 v1.8.4 / Skyrim SE 1.6.1170 x64）

按用户顺序处理掉落返还、裸体，再尝试修复悬空不可拾取。保留用户已验证有效的战斗家具退出和拾取消失逻辑。以官方 tag v1.8.4、提交 54b3a858e228dc8807ed65bc3f9ac3c3f81b610d 及原锁定子模块构建；不是未编译 DLL 的二进制修改。

## 改动与证据

1. 当前 coopfix3r1 测试日志中有45次服务器以来源库存不可用拒绝掉落，客户端随后返还。这是此前自加严格缓存匹配的回归路径。缓存中穿戴、强化、充能等信息不能当实时交易凭据。改为信任当前所有者已经成功执行的原生丢弃，按基础物品在缓存中优先扣匹配条目、再扣同类条目；兼容分散条目和负差值，最多扣缓存净可用数量，记录缓存落后。缓存缺失不再取消真实丢弃。保留所有权/epoch/session/参数校验、nonce去重、服务器唯一编号和第一赢家原子裁决。与官方一样信任客户端，不提供反作弊保证。
2. 本地待确认记录单独保留返还物品的原穿戴信息；注册因其他原因失败时，若玩家的装备选择尚未变化则恢复穿戴，若已换装则只返还背包，不覆盖新选择。
3. 装备通知携带所有者现有的穿戴清单；服务端只合并活角色的穿戴信息，补齐缓存中缺少的实际穿戴条目，不改容器/尸体差值。接收端只在护甲集合不同时执行原来的脱甲步骤，然后装备所有者仍在穿戴的护甲，不重新穿本地旧护甲。等待3D期间先更新待生成快照；死亡/旧epoch消息不能恢复已被拿走的尸体衣服。具体裸体根因仍需游戏对照，不能声称全部解决。
4. 撤掉掉落物对SetSkipSaveFlag的调用：该旧助手实际写入运行时标志0xFFFF，其中包含等待删除/永久删除位，并非仅“不保存”。不改官方助手和NPC调用；通过现有TESObjectREFR的CheckSaveGame实现做专用过滤，只让handle匹配的联网临时掉落引用跳过保存，不碰其他引用。这是更直接的可疑原因，仍须游戏和保存/读档验证。
5. 同一服务器的区域快照按唯一ID核对，保留仍有效的掉落引用，删除已经不在快照里的物品，减少过区域时反复删建。去掉启用后再次MoveTo；只在模型、区域、碰撞对象均就绪后通过有返回值的引擎入口设置动态物理，保留地面碰撞，最多三次唤醒。日志分开记录碰撞是否存在、motion返回值、impulse是否可调用。没有碰撞对象时记录等待信息，不把模型可见说成物理成功。此部分是待游戏验证的尝试，不保证所有悬空物已修好。
6. 保留上一轮拾取队列与注册ACK交错的身份修复，保持唯一拾取裁决。NPC FurnitureService / FurnitureRecovery 及原生战斗、伤害、移动逻辑保持原样。

## 构建和替换

Windows Actions实际编译客户端、服务器和TPTests，执行预计75项测试（48项必需专项），做服务端生成配置启动检查、四件PE64/版本检查和交付哈希检查。一轮完整构建，不额外重复编译。实际结果以该提交对应的Actions和交付报告为准，构建失败不发布测试成品。

两位玩家都覆盖 `SkyrimTogetherReborn/SkyrimTogether.exe` 与 `EarlyLoad.dll`；运行服务器的一方同时覆盖 `STServer.dll` 与 `SkyrimTogetherServer.exe`。四件必须来自同一包，不混用r1/r2。保留原官方资源、脚本、ESP和配置，服务器 `bEnableItemDrops=true`。MO2覆盖实际启动的STR mod目录，不能仅复制到Overwrite后假定已生效。

测试：先连续丢弃普通物品、未穿和已穿衣服、强化/附魔装备，核对丢出者背包数量和两边穿戴；接着A/B轮换拾取、同时拾取、快速丢后立即拾取；保存/读档后确认已拾取掉落物不复活；最后观察接入服务器后10秒及过区域/返回时物品是否保持落地、有名称提示且可拾取。分别记录“丢弃失败”“本地裸体”“仅对方裸体”“有模型无提示”，不要只看模型。保留存档备份。日志在实际启动EXE旁的 `logs/tp_client.log` 和服务端输出日志。

没有在此运行Skyrim或双人游戏。碰撞体建立、原生穿戴和场景副作用只有源码参考，无IDA/Ghidra验证；符合用户已允许的源码尝试范围。NPC起身由用户上一包实测确认，本包不扩大其条件；不会承诺所有NPC仇恨和AI均已修复。

每批Create成功发送后，再按可靠消息顺序发送SnapshotOnly穿戴清单；仅更新护甲集合，不重复执行物品装备命令。即使丢弃的是未穿的同款衣服、未产生原生换装事件，也会校正对方的当前穿戴。发送失败会保留待重试标志，不因登记ACK先到而丢失；对应新增纯协议工厂测试。

## 按用户追加要求的落点同步

保留拾取碰撞。由原始丢弃者的真实引用运行原生物理；非原始引用绝不发布落点。检查3D、实际碰撞对象、附着区域以及未暂停后，以250ms间隔采样既有position/rotation，连续两个稳定间隔后报告落点；后续移动限频500ms一次，发送失败不吃掉待发送位置。服务端校验当前玩家所有权/epoch/session、账本创建者、活物品及有限坐标，只更新位置/角度/区域，不改物品ID和数量。拾取后的晚到位置不能复活物品。快照和创建重试保留最后落点。

接收方通常等落点后创建副本，最多等2秒；没有来源报告则保留动态物理后备方式，避免永久隐藏。收到真实落点后保留碰撞，将副本设为Keyframed（hkpMotion::MotionType值4），减少第二套重力模拟；只有新位置到达时才移动并重新等碰撞就绪。未删除碰撞箱，不硬套玩家高度，不全局改变Havok或NPC。来源断开后没有另选物理所有者，后备方式保留拾取；远端副本不会独立滚动，这个取舍需游戏测试。

源码未证明REFR position/rotation始终与每种NIF的Havok可见节点同步，稳定采样不是引擎刚体休眠证明。没有IDA/Ghidra证据；这部分是用户授权的实际代码尝试，不宣称所有模型都已解决。

## 服务器两档tick

沿用原GameServer:bPremiumMode：true目标70，false目标60；不增加80档，不动匹配子模块。设置后重启服务器生效。底层1000ms/tick整数取整及2ms轮询休眠/系统调度会影响实测值；网络接包循环不完全受此tick限制，客户端约30ms发送角色状态，70不等于NPC/物品每秒收到70份新状态。

按用户最新“检查两次”：第一次检查源码所有权、消息顺序、保存与拾取边界及保留修复；第二次在Windows/MSVC实际编译客户端/服务端，运行75项测试（48项必需专项），核对PE64、目标版本、四文件哈希和配套服务端启动。不是承诺引擎无遗漏，也不是两次游戏测试。新增6项落点账本/工厂/时间纯测试，保留原69项。最终构建记录须对应本补丁最新提交；未编译或失败的候选不作为成品。
